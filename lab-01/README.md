## Завдання 1. Git і редактор

**Глобальні параметри Git:**
*   `core.autocrlf`: У Windows використовується закінчення рядків CRLF (`\r\n`), а в Unix/macOS — LF (`\n`). Якщо не задати цей параметр у змішаній команді, Git може сприймати файли як повністю змінені лише через різницю у закінченнях рядків. Для macOS/Linux використовується `input` (конвертує CRLF в LF при коміті), для Windows — `true`.
*   `pull.rebase=true`: За замовчуванням `git pull` створює merge-коміт, якщо локальна та віддалена гілки розійшлися. `rebase=true` переписує локальні коміти поверх завантажених змін, що дозволяє зберегти ідеально лінійну і чисту історію (без "Merge branch...").

## Завдання 2. Середовища виконання

**Навіщо менеджер версій:** Коли проєктів більше одного, вони часто вимагають різних (іноді несумісних) версій мов програмування (наприклад, старий проєкт на Node 14, новий на Node 22). Менеджер версій дозволяє миттєво перемикатися між ними ізольовано, не ламаючи системне середовище.

**Перемикання між версіями Node.js:**
> ```bash
> nvm install 20
> nvm install 22
> nvm use 20
> # Now using node v20.x.x (npm v10.x.x)
> nvm use 22
> # Now using node v22.x.x (npm v10.x.x)
> ```

**Вивід версій інструментів:**
> ```text
> [ВСТАВТЕ ВИВІД node -v, python -v (або uv --version), docker compose version]
> ```

## Завдання 3. GitHub і доступ

**Приватний SSH-ключ:**
Приватний ключ є аналогом паспорта з повним доступом. Якщо він потрапить у репозиторій, будь-хто зможе клонувати ваші приватні репозиторії, робити коміти від вашого імені та вносити шкідливий код.

**Що робити у разі витоку:**
1. Негайно зайти в налаштування GitHub (Settings -> SSH and GPG keys) та видалити скомпрометований ключ.
2. Видалити пару ключів локально зі свого комп'ютера (з папки `~/.ssh/`).
3. Згенерувати нову пару ключів за допомогою `ssh-keygen -t ed25519`.
4. Додати новий публічний ключ у налаштування GitHub.
5. Перевірити історію комітів та аудит-логи на наявність несанкціонованих дій.

**Перевірка з'єднання:**
> ```text
> [ВСТАВТЕ ВИВІД ssh -T git@github.com]
> ```

## Завдання 5. Правила репозиторію

**Різниця між соло та командною роботою:**
Коли робота стане командною, необхідно буде включити "Require approvals" (мінімум 1-2 рев'ю від колег) та обов'язкові перевірки CI/CD статусів перед злиттям. 

Правило **«Заборона обходу правил адміністратором»** (Do not allow bypassing the above settings):
*   **У команді (Корисно):** Захищає від випадкових `push` в `main` від сеньйорів або лідів. Усі рівні перед правилами.
*   **Соло (Шкідливо):** Ви заблокуєте самі себе. Оскільки автор PR не може сам собі його заапрувити, а правило вимагатиме PR, ви технічно втратите можливість зливати код у `main`.
