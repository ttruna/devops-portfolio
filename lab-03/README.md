# Лабораторна робота №3 — Автоматизація резервного копіювання, моніторинг API та Git-хуки

Набір CLI-інструментів для автоматизованого створення резервних копій з ротацією, діагностики доступності HTTP/HTTPS-сервісів та локального контролю якості коду через Git-хуки.

## Завдання 1. Скрипт резервного копіювання (`backup.sh`)

### Призначення
`backup.sh` створює стиснений архів (`tar.gz`) вказаної теки з часовою міткою формату `YYYY-MM-DD-HHMMSS` та підтримує ротацію: залишає лише `N` останніх архівів саме цього джерела, не зачіпаючи сторонні файли в теці призначення.

### Безпечний режим Bash (`set -euo pipefail`)
На початку `backup.sh` встановлено `set -euo pipefail`:
- **`-e` (`errexit`)** — негайно зупиняє виконання скрипту, якщо будь-яка команда завершилася з ненульовим кодом помилки. Без цього прапорця, якщо `tar` або `mkdir` впаде через брак місця чи прав доступу, скрипт продовжить роботу й видалить старі резервні копії в межах ротації, залишивши систему взагалі без актуального бекапу.
- **`-u` (`nounset`)** — вважає звернення до неініціалізованої змінної помилкою і зупиняє скрипт. Без цього прапорця друкарська помилка в назві змінної (наприклад, `$DEST_DIR` замість `$DEST`) підставить порожній рядок, що може призвести до архівації або видалення файлів у кореневій чи поточній теці.
- **`-o pipefail`** — змушує конвеєр (`cmd1 | cmd2`) повертати код помилки першої команди, яка впала, а не лише код останньої команди в ланцюжку. Без цього прапорця помилка у першій команді конвеєра буде проігнорована, якщо наступна команда завершиться успішно.

### Параметри запуску
| Параметр | Обов'язковий | Опис |
| :--- | :---: | :--- |
| `--source <шлях>` | Так | Тека, яку потрібно заархівувати |
| `--dest <шлях>` | Так | Тека для збереження архівів |
| `--keep <N>` | Ні (типово `5`) | Скільки останніх копій джерела зберігати |
| `--dry-run` | Ні | Показати дії без створення та видалення файлів |
| `--help` | Ні | Вивести довідку та вийти |

### Приклади запуску та виводу

**Створення резервної копії з ротацією:**
```bash
./backup.sh --source "./my project" --dest "./backups" --keep 3
```

## Завдання 2. Монітор доступності API (`api_monitor.py`)

### Призначення
`api_monitor.py` опитує список HTTP/HTTPS-цілей із JSON-конфігурації, робить 1 повторну спробу при мережевій помилці, класифікує причину збою за етапом зупинки запиту, записує звіт у JSON і надсилає сповіщення у Slack/Discord через змінну середовища `MONITOR_WEBHOOK_URL`.

### Приклад конфігурації (`config/targets.json`)
```json
{
  "targets": [
    {
      "name": "Healthy API (GitHub Zen)",
      "url": "[https://api.github.com/zen](https://api.github.com/zen)",
      "expected_status": 200,
      "timeout": 5.0,
      "latency_threshold_ms": 2000
    }
  ]
}
```

### Запуск та приклад виводу
```bash
export MONITOR_WEBHOOK_URL="[https://discord.com/api/webhooks/YOUR_ID/YOUR_TOKEN](https://discord.com/api/webhooks/YOUR_ID/YOUR_TOKEN)"
python3 api_monitor.py --config config/targets.json --output monitor_results.json
```

### Різниця між «з'єднання відхилено» та «тайм-аут» в інцидентах
1. **З'єднання відхилено (`Connection Refused`, TCP RST):**
   - **Що відбувається на мережевому рівні:** Пакет `TCP SYN` дійшов до цільового хоста, операційна система хоста жива й відповіла пакетом `TCP RST` (Reset), тому що на вказаному порту жоден процес не слухає (`listen()`). Відповідь приходить миттєво (за одиниці мілісекунд).
   - **Дії інженера в інциденті:** Мережева маршрутизація та фаєрвол працюють. Проблема на рівні застосунку: процес вебсервера/бекенду впав (OOM, crash loop), не запустився після деплою або слухає інший порт/інтерфейс (`127.0.0.1` замість `0.0.0.0`). Потрібно перевіряти статус сервісу (`systemctl status`, `docker ps`, логи контейнера).

2. **Тайм-аут (`Timeout`):**
   - **Що відбувається на мережевому рівні:** Клієнт відправив `TCP SYN` (або HTTP-запит) і не отримав жодної відповіді протягом заданого часу — пакети просто зникли або обробка зависла.
   - **Дії інженера в інциденті:** Можливі два сценарії:
     - *Мережевий рівень:* пакет блокується фаєрволом правилом `DROP` (без відповіді `RST`), неправильна маршрутизація, впав сам сервер/віртуальна машина. Потрібно перевіряти Security Groups, правила фаєрволу, доступність хоста.
     - *Рівень перевантаження застосунку:* TCP-з'єднання встановилося, але воркери сервера вичерпані, база даних заблокована повільними запитами або вичерпано пул з'єднань — сервіс не встигає віддати HTTP-відповідь. Потрібно перевіряти CPU/RAM, черги запитів і повільні транзакції в БД.

## Завдання 3. Інтеграція з Git (`hooks/`)

### Встановлення хуків
Тека `.git/hooks` не версіонується в Git, тому після клонування репозиторію хуки потрібно активувати одним із трьох способів (виконувати з кореня репозиторію `devops-portfolio`):

1. **Через налаштування `core.hooksPath` (рекомендовано — оновлення хуків у репозиторії застосовуються автоматично):**
   ```bash
   git config core.hooksPath lab-03/hooks
   ```
2. **Через символічні посилання:**
   ```bash
   ln -sf ../../lab-03/hooks/pre-commit .git/hooks/pre-commit
   ln -sf ../../lab-03/hooks/pre-push .git/hooks/pre-push
   ```
3. **Через копіювання файлів:**
   ```bash
   cp lab-03/hooks/pre-commit .git/hooks/pre-commit
   cp lab-03/hooks/pre-push .git/hooks/pre-push
   chmod +x .git/hooks/pre-commit .git/hooks/pre-push
   ```

### Чому Git-хуки не є засобом контролю якості
- **Виконуються лише локально:** Хуки живуть на машині розробника. Якщо розробник не активував їх після `git clone`, вони взагалі не запустяться.
- **Легко обходяться прапорцями:** Будь-який локальний хук вимикається однією опцією — `git commit --no-verify` або `git push --no-verify`.
- **Різне середовище розробників:** На машині одного розробника може не бути `shellcheck` або стояти інша версія Python/лінтера, через що перевірки дають різні результати.

**Що роблять обов'язкові перевірки в CI/CD-конвеєрі (наприклад, GitHub Actions + Branch Protection Rules), чого не можуть хуки:**
1. **Неможливість обходу:** Налаштування захисту гілки `main` (Required status checks) фізично блокують злиття Pull Request, доки серверний конвеєр не поверне статус `success` — жоден локальний прапорець `--no-verify` на це не впливає.
2. **Ізольоване та відтворюване середовище:** CI запускає лінтери й тести у чистому контейнері з фіксованими версіями залежностей, виключаючи проблему «у мене локально працює».
3. **Перевірка результату злиття:** Конвеєр тестує не просто окремий коміт, а результат об'єднання гілки розробника з актуальним станом `main`, виявляючи логічні конфлікти ще до мерджу.
